## 一、设计动机与更小的可玩原型

### 1.1 从完整大世界缩到可检验的局部切片【待验证／待定】

今天提出：与其从完整 16×16 大地图直接验证玩法，不如先构造一个**更迷你的空间原型**：

- 初次设想：**4×4 Chunk**。
- 随后进一步考虑：**3×3 Chunk**（用户原话：“哦不对，也许 3×3？”）。
- 初始结构设想：包含**两条必经之路**与**一个随机 Chunk**。
- 这里的“必经之路”着重表达空间瓶颈／不可随便绕开的通道。**两条路的具体位置、功能差异、方向、是否单行、是否同时必经，均尚未敲定**，不应自行补成确定规则。
- **3×3 与 4×4 仍是备选**，不是正式选型，也不是对整个大世界尺寸的更改。

建议的验证重点（建议，而非用户已敲定的玩法规则）：用极小的固定骨架检验关卡的路径选择、分割是否有意义、随机 Chunk 能否提供可重复探索价值，以及进入危险区域前的判断与撤退空间。如果 3×3 过于拥挤、装不下有意义的两处通行瓶颈，再比较 4×4。不要以填满 Chunk 数为目标。

### 1.2 与已有工程规模的关系【确认的边界】

- **64×64m／Chunk** 是现行 GDD 已定规格，微型原型沿用这个单位。
- GDD 的正式大世界规模仍为 **16×16～32×32 Chunk【暂定】**；此前布局草案倾向 16×16。**今天的 3×3／4×4 不是正式世界缩容决定**。
- `Docs/DevLog.md` 已记录的 **8×8 地形技术实验完成且 Unity 验证通过**。那是体素、错切相机、Biome 渐变和地形生成等技术验证；今天提出的微型布局原型是另一项**玩法／空间结构验证建议**，不能混为一谈。
- 随机区域的运行时生成与刷新，DevLog 截至当前仍未标为完工。不能因为微型原型里计划放 1 个随机 Chunk，就宣称该功能已有实现。

## 二、抽象大世界布局的设计顺序【确认的方向】

今天明确了一个**先平面结构、后立体分割、再改交通**的三阶段方法。它细化了 `codexsug/WorldLayoutRules.md` 旧草案中“地理结构先于道路”的表述——**初步意图路线可以先画，但最终道路必须在地形约束后重做**：

1. **第一阶段：平面地理骨架**
   - 先布置关键地点：住所、聚落、副本入口、特殊野外建筑／奇观等。
   - 规划 Biome 大致区域、河流、峡谷以及其他大尺度地理分割。
   - 在关键地点之间画**初步路线**，只表示希望存在的联系和路径关系；不预设它已符合高差通行条件。
   - 初步路线是独立图层，**可隐藏但不删除**，方便对照。
2. **第二阶段：立体分割的抽象标记**
   - 在前述骨架之上加入**台地／盆地**二维分类区域。
   - 用这些概念推敲受限入口、出口、断崖、瓶颈、单向通路及局部不可直通的空间关系。
   - **只标台地／盆地概念，不在规划器里写真实海拔、相对高度米数、坡度或高度图**。
3. **第三阶段：重设计最终路线**
   - 对照第二阶段的空间限制，重新规划能够承担实际交通关系的道路／小径／通路。
   - 最终路线与初步路线**各自保存、可独立显示／隐藏**，初步路线仍是对照资料。
   - 在空间骨架和交通关系确定后，再标记哪些 Chunk 必须固定，剩余适合区域再布置随机 Chunk；随机区域不主导重要地点及固定交通骨架。
   - 规划完成时得到的是**世界空间关系的抽象蓝图**，不是直接可玩的地形，也不是生成后的高程图。

这套顺序同时适用于完整世界设计和缩小后的 3×3／4×4 验证原型，但后者的具体布局未定。

## 三、规划器必须严格保持的图层语义【确认的方向】

### 3.1 Biome：二维、硬边界、离散类别

- **Biome 图层不按 Chunk 格子涂色**；可以跨 Chunk 任意自由涂刷，同一个 Chunk 内允许多种生态。
- 7 类：人类区（human）、湿地／沼泽（wetland）、混交林（forest）、寒带针叶林（conifer）、山地（mountain）、Moorland／荒原（moorland）、海岸（coast）；另有“未指定／擦除”。
- 笔刷表现为**不带描边的连续实心色块，边界硬切**；左键绘制、右键仅擦除本图层。
- **规划器内不做噪声、羽化、权重混合或生态渐变**。现行 GDD 已定的 Biome 平滑过渡规则由**下游体素生成器**实现；两者并不冲突。

### 3.2 台地／盆地：与 Biome 完全分离的三态分类层

- **不是**多边形加“相对高度多少米”的方案；该旧版设计已被用户明确否定。
- 与 Biome 一样采用可调直径的二维自由笔刷、硬边界、右键擦除；不同的是只有**普通 / 台地 / 盆地三种状态**。
- 抽象编码：`0 = none（普通／未标）`、`1 = plateau（台地）`、`2 = basin（盆地）`。**编码是类别，不是海拔级数、高差正负或米数**。
- 表现区分：例如**台地斜线纹理、盆地点状纹理**，与 Biome 的底色叠加展示。
- 台地与盆地互斥；同一位置后绘制者覆盖先绘制者。
- Biome 与台盆的可见性、擦除、保存**互不影响**。例如“湿地 + 盆地”“森林 + 台地”合法。
- 最终台地高低、连通坡道、局部阶梯、悬崖轮廓和实际高度均由现有生成器在结合宏观起伏与噪声后确定。**规划器不承担地形连续性计算**。

### 3.3 其他独立图层与编辑操作

- **关键地点**：坐标、类型、名称、圆形／方形及可调影响范围，可跨多个 Chunk。
- **河流／峡谷**：保留中心线、宽度等矢量数据；先表达大尺度分割，不在规划器内生成河床与峡谷体素。
- **初步路线／最终道路**：两套独立数据与显隐开关；可设置单向属性。不能因为后期重画路线就自动删除原初步路线。
- **Chunk 属性**：在明确的 Chunk 网格上单击切换固定、随机、过渡、不可通行等标记；与 Biome 和台盆层分离。
- 地图长宽可调；工具独立于 Unity，可离线打开单文件 HTML 操作；支持撤销、重做、JSON 导入／导出及 PNG 总览。

## 四、数据优先于 PNG【确认的方向】

**这个工具的成果不是好看的地图图片，而是一份能交给现有体素生成器的多层空间输入。**

- **PNG：**只用于人查看完整布局、讨论路线，不是生产数据，不应从 PNG 逆向恢复各类属性。
- **JSON：**核心交付物。不同图层必须独立，不要把生态、台盆、Chunk 标记混成一张贴图或单一类别。
- 世界参考坐标以米表示，Chunk 为 64m 网格；Biome 和台盆的边界不必贴齐 Chunk 网格。
- Biome／台盆图层保留**可编辑原始笔画**和**离散分类遮罩快照**；当前工具 README 规定栅格单元是 4m、行优先 RLE，并不等于最终体素精度。原始笔画用于以后重新采样。
- 下游体素生成器再叠加宏观地势、地形起伏、噪声、Biome 融合、真实悬崖与坡道，并将规划上的路线／地理关系落实到体素地形。
- **不可把“JSON 可导出”误写成“现有 C# 体素生成器已完成对这些 JSON 图层的读取与约束生成”**：后者是独立的后续集成工作，尚无已实现证据。

当前工具 JSON v2 的主要结构：

```text
schema: wort-world-layout
version: 2
world: { columns, rows }
layers:
  biomes:       { model, marks, raster }
  terrain:      { model, marks, raster }       # none / plateau / basin
  chunkZones:   [ { x, y, zone } ]
  places:       [ { id, name, category, shape, radius, x, y } ]
  hydrography:  { rivers, canyons }
  routes:       { draft, final }
```

详见 `Tools/WorldPlanner/README.md`。**编辑态以 marks 为准，导出时计算 raster**；遮罩是分类值而非混色像素。

## 六、给 Claude 的处理建议

1. **先读取**本文件、`codexsug/WorldLayoutRules.md`、最新 GDD/DevLog 与 `Tools/WorldPlanner/README.md`，再讨论微型原型或世界地图生成器接入。
2. 需要规划小型可玩实验时，**先比较 3×3 与 4×4 能否容纳“两条必经之路 + 一个随机 Chunk”的有效结构**；不要把 3×3 写成已定规格。别把这个实验等同于已有 8×8 技术实验，也不要据此缩小正式世界。
3. **宏观设计顺序以本文件第二节的新三阶段方法为准**：先初步路线、后台盆分割、再最终路线。这是对旧布局草案的细化，不意味着否定“最终道路受地形约束”的原则。
4. **规划器不写真实海拔**；不要再加相对高度米数、生成噪声或体素计算。用户已经明确要求把这些留给现有体素生成器。
5. 若后续接入生成器，应单独提出输入契约、分类遮罩采样、道路连通约束和验证方案，经过确认后再写生成器代码；不要凭建议文档宣称该接入已完成。
6. **本文件是 codexsug 建议／讨论归档**，请不要自动把其全部内容升格为 GDD【已定】、也不要擅自改动 GDD 只读快照与 DevLog。

---

**当天结论：微型地图先验证“少量关键通路 + 随机空间”是否成立；完整世界的抽象设计则以“关键地点／水系／初步路线 → 台盆三态分割 → 最终道路 → 固定／随机 Chunk”为顺序；最终给体素生成器的是独立的分层数据，而非一张 PNG 或一幅预先计算好的高度图。**
